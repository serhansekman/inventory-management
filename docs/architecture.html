Factory Inventory Management System

Architecture overview: a Vue 3 single-page app talking to a FastAPI service that serves in-memory data loaded from JSON files. There is no database.

Data flow

How a filter change on screen becomes a filtered response.

Request path

  1. User changes a filter (period, warehouse, category, status). State lives in the shared useFilters composable.
  2. A view calls a method on api.js, which builds query params and skips any filter set to all.
  3. FastAPI receives GET /api/...?warehouse=&category=&status=&month=.
  4. apply_filters and filter_by_month filter the in-memory lists. Quarters such as Q1-2025 expand to three months.
  5. Pydantic validates the response model and FastAPI returns JSON.
  6. The view stores raw results in refs; derived values (totals, chart series) are computed properties, so the UI updates reactively.

Startup path

  1. uv run python main.py starts Uvicorn on port 8001.
  2. Importing mock_data.py reads every JSON file once into Python lists and dicts.
  3. Requests read these lists directly. Nothing is written to the JSON files, so a restart returns the data to its initial state (including clearing restocking orders).
  4. npm run dev starts Vite on port 3000. The API base URL is hard-coded to http://localhost:8001/api in api.js.

Restocking flow

The one write path in the app: budget to recommendation to submitted order.

  1. The Restocking view loads /api/demand, which now carries unit_cost and lead_time_days per SKU.
  2. A budget slider ($0 to $500K) drives a computed recommendation list: items with a positive demand gap, increasing trends first, funded in order until the budget runs out. The last funded item may be partial.
  3. Place Order sends only SKUs and quantities to POST /api/restocking-orders. The server re-prices from its own data, checks the total against the budget, and sets the order lead time to the longest item lead time.
  4. The order is appended to an in-memory list kept separate from customer orders, so dashboard and report totals are unaffected.
  5. The Orders view lists these in a Submitted Orders section with lead time and expected delivery. That section ignores the global filters.

API surface

Endpoints implemented in server/main.py and which filters each accepts.

Endpoint Purpose Filters
GET /api/inventory, /{id} Stock levels, reorder points, unit cost warehouse, category
GET /api/orders, /{id} Customer orders and status warehouse, category, status, month
GET /api/dashboard/summary KPI totals for the dashboard all four
GET /api/demand Demand forecasts none
GET /api/backlog Backlog items, flagged if a purchase order exists none
GET /api/spending/* Summary, monthly, categories, transactions none
GET /api/reports/* Quarterly reports and monthly trends none
POST /api/restocking-orders Submit a restocking order; prices and lead time are looked up server-side, total must fit the budget none
GET /api/restocking-orders Submitted restocking orders, newest first none

Observations

Things worth knowing before changing the code.

Client and server are out of step. api.js calls /tasks (GET, POST, PATCH, DELETE) and /purchase-orders (POST, GET), but main.py defines no such routes. A CreatePurchaseOrderRequest model exists with no endpoint using it. Those client calls would return 404 against the current backend. The restocking endpoints are the exception: they are implemented on both sides.
Design Data is held in process memory and nothing is persisted. The only writable dataset is the restocking order list, which starts empty and resets on restart.
Config The API base URL is hard-coded, and CORS allows every origin. Fine for a local demo, not for deployment.
Tests Backend tests cover dashboard, inventory, restocking, and miscellaneous endpoints under tests/backend. There are no frontend tests.
Limit Inventory has no time dimension, so the period filter does not apply to it.
